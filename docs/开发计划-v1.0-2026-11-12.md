# 场馆连锁客户管理平台 · 现状分析与开发计划 v1.0

> 产出日期：2026-11-12　代码基线：`main @ 383d682`
> 产出方式：实测体检（启动服务 + 20 项接口冒烟 + 并发/退款专项 + 迁移验证）+ 产品优先级 + 架构任务分解
> 人天口径：1 名熟手全栈，含自测，不含联调返工；总工作量 **75 人天**（P0 26.5 / P1 26.5 / P2 22）

---

## 一、现状结论

**一句话：能演示、不能收钱的 Technical Alpha。功能够开一家店，但两条数据链没锁死、没有域名发不出去、没有安全网不敢上线。**

判断「能不能卖」只卡三件事：

| 线 | 卡点 | 业务后果 |
|---|---|---|
| 数据正确线 | 并发约课超卖、退款不回冲营收 | 满员课实际来 5 人现场吵架；老板对账发现系统算错，"账实核对"这个核心卖点自证不成立 |
| 交付准入线 | HTTP + IP，无备案域名 | 小程序发不出去 = 没有交付物，这是 0/1 不是质量档位 |
| 可运维线 | 无备份、无测试、无回滚 | 修前两条的过程会引入新故障，拿客户生产数据做实验 |

### 2.1 规模

| 演示环境 | `http://124.220.52.50` | `/health` 200、`/admin/` 200，HTTP + IP |

### 2.2 已实测可用（20 项冒烟，19 通过）

认证与权限（JWT 双令牌、4 角色 RBAC、越权 403、未登录 401）、会员建档、收款登记 + 权益入账 + 幂等、课程模板与单节课创建、微信 mock 登录 + 手机号绑定、约课、满员进候补、取消后自动递补 OFFERED、递补确认、教练点名名单、点名时间窗拦截、经营看板、日终账实核对、按比例退款、后台静态页。

**主干业务五态（BOOKED/WAITLIST/OFFERED/CANCELLED/ATTENDED）是通的，不是空壳。**

### 2.3 已复现缺陷

| 级别 | 缺陷 | 实测证据 | 根因位置 |
|---|---|---|---|
| **P0** | 并发约课超卖 | 容量=1 的课节，5 会员并发 → **4 个返回 BOOKED**，`booked` 最终只等于 1 | `app/services/schedule.py:214-216` 读-改-写无锁；唯一约束只防同会员重复 |
| **P0** | 退款不回冲营收 | 退款 1999 元后看板月收入**完全不变**；收款单仍 `PAID` | `app/services/payment.py:177-210` 不回写单据；`dashboard.py:46-51` 只统计 PAID |
| **P0** | 零测试入库 | 提交信息称"99/99 通过"，仓库无 `tests/`、无 pytest | 回归无法复现，任何改动都是盲改 |
| **P0** | 小程序无法发布 | `config.js` 的 real 环境仍是 `https://YOUR_HTTPS_DOMAIN` | 微信要求 HTTPS + 备案域名 |
| P1 | 候补超时无后台驱动 | `expire_offers` 只在约课/查预约时惰性触发 | 会员不打开小程序 → 名额空转 |
| P1 | 有接口无界面 | 门店/账号、课程模板、调课审批、评价审核、审计日志 | 馆主无法自助操作，实施靠工程师 |
| P1 | 会员端缺页 | 站内信、已发布评价完全未调用；无门店切换/资料编辑 | 收不到通知、评了看不到 |
| P1 | 无分页 / N+1 | 列表 limit 硬编码 50-200；`/api/app/sessions` 每节课再查 4 张表 | 上千条数据后必卡 |
| P2 | 多租户未闭环 | 只能 seed 单租户，无开通入口、平台后台空有角色 | 第二个客户要开第二套实例 |
| P2 | 工程化缺失 | 依赖未锁版本、未显式声明 python-dotenv、无告警/备份/回滚 | 运维全靠人肉 |

### 2.4 隐藏缺陷（体检中额外发现，已进计划）

- `payment.py:206` 把退款单 ID 写进了流水的 `ledger_entry_id` 字段 → 按此字段回溯流水全部落空。
- `LedgerEntry` / `PaymentRecord` 的幂等键唯一约束**不含 tenant_id**（`models/product.py:72`、`models/payment.py:19`）→ 多租户同键必撞。
- `DailyLedger` 已有 `refund_count / refund_cents / active_entitlements` 字段，但从未写入。
- 同会员并发重复约课会抛未捕获 `IntegrityError` → 500，而非 409。
- 负余额检测用"所有负向流水"，退款写入负向流水后会**误判差异**（改退款时必须同步修）。

## 三、优先级判定

| 阶段 | 定位 | 出口标准（一句话） | 人天 |
|---|---|---|---|
| **阶段一 可止血** | 能安全接第一个客户 | 并发不超卖、账能对上、域名能提审、有备份能回滚 | 26.5 |
| **阶段二 可交付** | 功能闭环、可正式销售 | 后台无"只有 API"、会员端无缺页、消息真送达、性能不退化 | 26.5 |
| **阶段三 可复制** | 多店/多租户/商业化 | 新租户 5 分钟开通、数据完全隔离、一键发布回滚 | 22 |

> 注：产品经理抬头写 P1 = 24 人天，但 11 项明细相加为 **26.5**。本计划按明细 26.5 编排（差额 2.5 来自 Excel 导出 2.5d，已保留在阶段二，因为财务对账是续费前最易被投诉的点）。

## 十一、待确认（影响排期的决策点）

1. **ICP 备案是否已启动**（企业主体 / 域名 / 服务器）？未启动则上线里程碑后移 10–20 工作日，代码里程碑不受影响。

3. **生产 MySQL 8 / 域名 / 证书归属方**（客户 IT 还是我方代管）→ 决定是否额外对接人天。

5. **第一个客户是单店还是 2–5 店连锁**？单店可把门店切换后置；连锁则 P0-6 必须保留并确认跨店权益规则。
